# AI Machinery Atlas: platform and delivery assessment

Assessment date: 7 September 2026. Repository: `the reviewed atlas checkout`. Source inspected: `227647a4ef22c73d3593936e93f7ecd7b109c770`. The working tree was clean before and after this assessment. No source, build, public-site, licensing, or Git state was changed. This report assesses repository evidence and the existing local `dist`; the coordinating assessment separately records live-browser findings.

**Assessment:** the atlas is a substantial static educational reference with useful interactive models. Its next platform investment should make scientific maintenance, complete learning tasks, and releases more dependable. Its current architecture can support that work incrementally. A new account system, LMS, chatbot, CMS migration, or framework rewrite is not a prerequisite.

Evidence labels used below: **Measured** means inspected code/data or a check run during this audit; **Recorded** means a prior document's claim, not rerun here; **Judgment** means an engineering interpretation; **Proposed gate** is a future acceptance criterion.

## Current capabilities and boundaries

### Modularity, data and validation

**Measured strengths:** React/TypeScript with strict checking; JSON content packs; separate numerical functions and their UIs; versioned fragment parsing; named process routes; reusable equation rendering; lazy 3D and lab loading; and local static assets are all in place. A synthetic reference system centralizes package, rack, hall, and workload defaults. These are useful foundations for incremental development. [Compiler settings](../../tsconfig.json), [content adapter](../../src/lib/atlas.ts), [lazy components](../../src/Atlas.tsx), [reference system](../../src/lib/reference-system.ts).

**Measured limitations:** `RecordEntry` is an interface followed by casts, including `as unknown as RecordEntry[]`; it is not a complete authored-data schema. Claims and sources use separate component-local types. The validator asserts selected minimum fields and references, not complete schemas for every lesson, specification, source, equation, milestone, facility, lab, route, and versioned state. It checks valid HTTPS prefixes on lesson sources, not whether links resolve or support the associated claims. Journey construction silently filters nonexistent IDs before the validator examines the result, weakening detection of an accidentally mistyped journey ID. [Record casts](../../src/lib/atlas.ts), [journey filtering](../../src/lib/atlas.ts), [claim types](../../src/components/atlas-exploration.tsx), [validation scope](../../scripts/validate-atlas.mjs).

**Measured:** the relation type names include `part-of`, `assembled-into`, `executes`, and `limited-by`, but generated record edges currently use only `prerequisite` and `related`. Other relationship meanings are displayed in fixed production/operation lanes. Thus the platform has a useful navigable relation view, but not yet a uniformly authored, queryable engineering dependency model. [Generated edges](../../src/lib/atlas.ts), [fixed lanes](../../src/components/atlas-exploration.tsx).

**Measured:** `Atlas.tsx` owns navigation, hash restoration, browser storage, modal state, search, path state, optional WebMCP registration, scene controls, and much of the lesson UI in one 26,780-byte component. The exploration module combines process, graph, evidence, map, lesson depth, and glossary components. This is manageable at current scope, but it couples changes that should be independently reviewable. Compressed source formatting increases review difficulty; physical line counts are misleading here. [App state and effects](../../src/Atlas.tsx), [exploration module](../../src/components/atlas-exploration.tsx).

**Judgment:** prioritize a validated content contract and clean module boundaries over a wholesale framework replacement. Retain stable IDs, existing math modules, local deployment, and current content breadth.

### What the tests establish

**Measured strengths:** the numerical tests exercise conservation, dimensional examples, monotonicity, bounds, conditional yields, zero-work cases, memory capacity, overlap, and nonduplicated energy. They offer meaningful protection beyond checking snapshots of the implementation. The portable tests check local asset resolution at root/subdirectory paths, local film assets, metadata, forbidden private strings, and exact license/inventory hashes. [Deep math tests](../../scripts/deep-math.test.mjs), [new numerical tests](../../scripts/numeric-math.test.mjs), [portable integrity](../../scripts/portable.test.mjs).

**Measured gaps:** no checked-in `.github` directory, browser-test configuration, or browser test command was found. Current checks do not exercise DOM interaction, back/forward and malformed hashes, storage migration, modal focus restoration, all lesson-to-lab links, failed lazy downloads, WebGL recovery, rendering suspension, responsive layouts, screen-reader journeys, or retained GPU resources after repeated navigation. They do not demonstrate scientific agreement with physical measurements. Repository absence does not prove the remote repository has no external checks or branch protection; those controls were not inspected.

**Measured equation boundary:** the original and expansion authored-equation files are empty objects; older lessons pass through a heuristic `toLatex` converter with a text fallback. The strict authored-equation/symbol test applies to the 14 infrastructure-depth lessons. The fallback is a sensible resilience mechanism, but a passing release test does not mean every lesson's formal mathematics or symbol units were checked. [Original equations](../../src/lib/data/equations-original.json), [expansion equations](../../src/lib/data/equations-expansion.json), [converter/fallback](../../src/components/equation.tsx), [targeted equation test](../../scripts/infrastructure-depth.test.mjs).

### Delivery, mobile use and accessibility

**Measured strengths:** phones explicitly activate the 3D workspace. Scene rendering honors visibility, intersection, reduced motion, active state, and a low-power pixel-ratio/frame policy. Geometries/materials are disposed, WebGL initialization failure leaves text available, context loss exposes a retry, and optional-resource errors have boundaries. The app provides text-based component selection, a skip link, controlled dialogs, equation text/MathML, map tables, and announced numerical output. [Phone activation](../../src/Atlas.tsx), [render gating](../../src/components/atlas-scene.tsx), [recovery/cleanup](../../src/components/atlas-scene.tsx), [resource boundary](../../src/components/resource-boundary.tsx), [accessible numerical results](../../src/components/numeric-workbench.tsx).

**Measured delivery boundary:** the initial reader still eagerly imports the full lesson corpus, equation machinery, comparison, evidence, and the global map module. `atlas-exploration.tsx` imports the 115,610-byte world-land JSON even when the map is closed. The production entry remains approximately 584 kB under this audit's gzip calculation. `chunkSizeWarningLimit:1500` changes a warning threshold; it is not a loading strategy or a performance target. [Entry imports](../../src/Atlas.tsx), [map imports](../../src/components/atlas-exploration.tsx), [build configuration](../../vite.config.ts).

**Judgment:** the highest performance return is a smaller readable entry, deferred optional destinations/math, and content chunks behind a compact navigation index. Phone-first rendering alone does not eliminate entry transfer and JavaScript parse costs. Consider prerendered lesson text as a later access/discoverability improvement once the content schema stabilizes; keep fragment compatibility if adding per-lesson URLs.

**Accessibility risk, not a conformance verdict:** the existing accommodations deserve preservation. Full keyboard and assistive-technology task checks are still needed. For example, quiz selection and feedback are class-based buttons/text without the explicit pressed/selected or live-feedback semantics present in newer numerical components; older plots expose generic labels rather than a complete data alternative. Verify behavior with actual assistive technology before choosing fixes. [Quiz UI](../../src/Atlas.tsx), [legacy plot](../../src/components/lab.tsx).

### Learning state, applications and assessment

**Measured strengths:** all 224 lessons have a three-option knowledge check and explanatory feedback. Guided paths, mechanisms, misconceptions, science tabs, prerequisites, source links, and 24 labs support exploration. There are explicit learning outcomes and worked-example fields on all 127 added lessons; the compatibility enrichment file adds them to 53 of 97 original lessons. Thus **180 of 224 effective records have these two fields**, with 44 originals retaining the earlier format. This count describes field presence, not instructional quality. [Lesson depth display](../../src/components/atlas-exploration.tsx), [original enrichment](../../src/lib/legacy-enrichments.ts).

**Measured state boundary:** local storage saves only `visited` IDs and the latest answer index for each lesson. Selecting a lesson marks it visited; the number of currently correct answers drives “concepts checked.” An answer immediately exposes the correct choice and can be replaced. Storage has a versioned key but no lesson/check revision, attempt history, saved lab scenario, mastery evidence, export/import, or cross-device synchronization. Restored answer values are not fully validated. A future option reorder or answer change could reinterpret old answers. These are appropriate exploratory checks, not evidence of mastery or learner qualification. [Selection and persistence](../../src/Atlas.tsx), [counting](../../src/Atlas.tsx), [feedback](../../src/Atlas.tsx).

**Measured sharing boundary:** hash state preserves lesson, view/process step, path/step, and a comparison destination. It does not preserve selected comparison specimens, lab mode/inputs, a prediction, or an explanation. Lab inputs are component state; reopening/remounting can reset them. [URL state](../../src/lib/url-state.ts), [app encoding](../../src/Atlas.tsx), [lab state](../../src/components/lab.tsx), [comparison state](../../src/components/specimen-comparison.tsx).

**Applications/cases:** there is already usable applied material: synthetic manufacturing and capacity scenarios, HBM assembly, inference placement, token paths, reliability, economics, and orbital budgets; eight architecture specimens have common comparison axes and source boundaries; the global map has curated, dated project snapshots and deliberately avoids a summed capacity total. These are worked examples, calculators, comparison cards, and project snapshots. No separate case-study schema or end-to-end assessed case workflow was found. A shared reference default is not yet a persistent cross-lab scenario in which one decision carries its consequences into the next task. [Numerical lab contracts](../../src/lib/numeric-labs.ts), [engineering lab definitions](../../src/components/deep-workbench.tsx), [specimens](../../src/components/specimen-comparison.tsx), [curated map](../../src/components/atlas-exploration.tsx).

**Judgment:** the next learning improvement is three complete predict → calculate/inspect → explain → transfer cases built from these assets, with learner-owned saved work. More inventory should follow evidence that these cases are understandable and useful.

### Evidence operations and release reliability

**Measured:** five content packs contain **39 claim cards and 122 uniquely identified source records**; their claim-to-lesson links cover **34 distinct lesson IDs**. Every lesson separately has sources, so 34 is the reach of explicit claim-ledger linkage, not the count of sourced lessons. Cards retain status, dates, metric/basis, scope, limits, and locators; preserving an unresolved claim is a positive evidence practice. [Evidence display/types](../../src/components/atlas-exploration.tsx).

**Measured operations gap:** no author/reviewer/owner, supersedes, or review-due fields were found in the lesson/claim/source objects across the five packs. There is contribution guidance, but no checked-in CODEOWNERS or per-content review assignment. References also live in lesson JSON, specimens, routes, labs, and facilities, creating several maintenance surfaces. This does not establish that human review never occurred; it means review responsibility and status cannot be recovered consistently from the platform. The approved plan explicitly asked for reviewer, supersedes, review-by, conflict notes, author/reviewer roles, and claim change history. [Required claim schema](PRIOR-EXPANSION-PLAN.md), [content operations commitment](PRIOR-EXPANSION-PLAN.md), [contribution requirements](../../CONTRIBUTING.md).

**Measured release boundary:** current `main` is `227647a4…`; fixed local tag `v1.2.0` dereferences to `7090ccd090fe647ad5d0350a9cf6c988322720e2`. Their trees differ in nine files, including the reading guide, app/CSS, and metadata/docs. The current page/version language identifies v1.2.0, while current main is not byte-identical to that fixed release. The user-approved metadata/history work should remain intact. Do not move the historical tag to hide the distinction. This audit did not independently download release archives or verify remote protections/deployment checksums.

**Measured/recorded:** release instructions already require fixed tags, checksums, clean-source/static artifacts, actual QA scope, and rollback material. No source-commit/content-version/asset-hash build manifest was found in the inspected app/build. The next release needs a machine-readable provenance record and an explicit release-versus-live revision statement so that teaching materials and reported defects can identify what was actually used. [Fixed release policy](../../docs/RELEASING.md), [artifact requirements](../../docs/RELEASING.md), [rollback guidance](../../docs/RELEASING.md).

**Plan completion judgment:** `IMPLEMENTATION.md` is an earlier working-edition snapshot: 210 lessons/57 branches and pending prior release work. It is not an accurate completion ledger for current v1.2.0. Newer release notes supersede its counts and browser-QA account, but neither document proves all prior gates complete. In particular, the formative learner review, measured device/network performance baseline, and recoverable content-review ownership requested by the plan remain undemonstrated. Record them as open gates unless separate evidence exists, rather than interpreting lesson counts as closure. [Stale implementation record](PRIOR-IMPLEMENTATION.md), [formative review commitment](PRIOR-EXPANSION-PLAN.md), [performance gate](PRIOR-EXPANSION-PLAN.md).

## Recommended investment sequence

The phases below are additive, preserve current scope and stable links, and name proposed responsibilities rather than inventing assigned people. Calendar commitments should follow an agreed engineering and scientific-review cadence.

| Phase | Work and dependency | Proposed gate |
| --- | --- | --- |
| **0. Establish a trustworthy release baseline** | Engineering/release owner; can begin immediately. Reconcile the status ledger, exact source/tag/live identities, present artifacts and QA scope. Add build provenance and a repeatable release check. | One release manifest records source commit, content revision, lockfile hash, archive/asset hashes and checks performed. The published static artifact matches the manifest. A new patch/minor version represents future changed public assets; old tags stay fixed. A documented rollback is rehearsed against a preview location. Every old plan gate has evidence or an explicit open status. |
| **1A. Validate the content contract** | Engineering plus named scientific editor; precedes broader content import and content-derived routing. Add schemas and one canonical build-time graph while retaining legacy adapters. Move types out of UI. | All 224 existing lessons validate without ID removal; invalid/duplicate IDs, sources, milestones, routes, lab links and prerequisite cycles fail with file/field errors. Validate raw paths before filtering. Equation render/notation coverage is reported for every science entry; intentional fallback is explicit. High-risk dated claims gain reviewer, review date/due date, supersedes/conflict fields and precise source linkage. No claim is silently given “reviewed” status by migration. |
| **1B. Automate complete learning tasks** | Engineering/QA; run alongside 1A on representative current fixtures. Extract URL/storage/navigation state only as needed to make contracts testable. | CI checks a served production build at root and `/ai-atlas/`: fresh deep link, malformed/versioned hash, path progression, search, quiz feedback, modal focus, one process route, three new labs, comparison, lazy-load failure and 3D fallback/retry. Test storage with absent/corrupt/older data. Add targeted screenshots at 320, 390, 768, 1024px and desktop; publish results with the exact source revision. |
| **1C. Measure and reduce the reader payload** | Engineering/performance; can parallelize 1A/1B after capturing current measurements. Split optional map/evidence/comparison/math destinations and introduce a compact index plus lesson chunks where justified. | Preserve all links/content. A cold phone reading session requests neither Three.js nor world-map assets before activation. Proposed initial engineering target: reduce compressed entry JS from this audit's ~584 kB to **≤350 kB under the same compression method**, then set user-facing performance budgets from actual low/midrange-device results. Record repeated cold/warm loads, device/browser/network conditions, readable-content time, interaction latency and scene frame/memory behavior. No sustained rendering while hidden/offscreen; repeated scene changes reach a stable resource baseline. |
| **2. Build three complete applied cases** | Learning designer and scientific reviewers, using 1A's schema and 1B's workflow checks. Start with manufacturing-to-package capacity, memory placement-to-token service, and deployment readiness-to-delivered work. Reuse current labs and comparisons. | Each case specifies learner level, prerequisite/outcome, coherent versioned inputs, synthetic/product/evidence boundary, prediction, constrained decision, calculation/inspection, explanation rubric and unfamiliar transfer task. A changed input has a visible downstream consequence within the case. Saved/exported scenario includes inputs, units, model/content version and provenance and restores deterministically. Exact specimen/lab selections can be shared. No account is required for this gate. |
| **3. Validate learning and maintainability** | Learning lead/editorial owner after phase 2. Conduct a small formative review spanning intended beginner/engineering users and accessible-device tasks; establish review cadence for current claims. | A documented pilot records where learners succeed or fail at prediction, explanation and transfer, with revisions tied to observations. Visit counts remain distinct from evidence of understanding. Save-state migrations preserve meaningful old progress and flag changed checks for review. Every dated claim has an owner and review trigger; overdue status is an editorial task, never an inferred factual change. Repeat the complete cases with keyboard and a screen reader, physical iOS Safari and Android Chrome, 200% text, portrait/landscape and constrained graphics. |

**Sequencing judgment:** phases 0 and 1 address reliability before expansion; phase 2 turns the existing library into stronger learning experiences; phase 3 establishes whether they work. Consider synchronized accounts, instructor dashboards, an authoring CMS, external integrations, or conversational assistance only after a documented user need survives those gates and its operating cost has an owner. The present static/local design is an advantage for portable access and should remain a supported mode.
